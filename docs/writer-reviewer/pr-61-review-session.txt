  **R1. Risk, non-blocking: sign-up still reveals which emails have accounts
  when email confirmation is off. Confidence: medium-high.**
  - **Where:** `src/app/auth-actions.ts:61-79`
  - **Evidence:**
    ```ts
    if (error) { ... return failure("The account could not be created. ...",
  email); }
    if (!data.session) { return { status: "success", message: "Check your email
  ..." } }
    redirect(HOME_PATH);
    ```
  - **Issue:** With confirmation off, which is the local stack the PR tested, a
  new address redirects to `/`. An existing address returns "User already
  registered", shown as the generic error. The two outcomes differ, so anyone
  can tell whether an address is registered. The PR itself says "The same
  address again gives the generic message".
    - The PR body's claim that the generic message "cannot reveal which
  addresses have accounts" holds for sign-in, but not for sign-up.
    - With confirmation on, Supabase returns an obfuscated user with no session
  and no error. A new and an existing address then both get "Check your email",
  which is safe.
  - **Why it matters:** issue #20 lists auth errors that don't leak information
  as an acceptance criterion.
  - **Suggested change:** ensure email confirmation is enabled on the hosted
  Supabase project, and say so in the README or PR. Or narrow the PR claim to
  sign-in and accept the sign-up leak, which most sites have.
  - **Not verified:** the hosted project's confirmation setting.

  **R2. Risk/performance, non-blocking: the proxy may call Supabase Auth over
  the network on every request. Confidence: low-medium.**
  - **Where:** `src/utils/supabase/proxy.ts:71` (`await
  supabase.auth.getClaims()`)
  - **Issue:** In the installed auth-js (`GoTrueClient.js` around line 5599),
  `getClaims` falls back to `getUser()`, a network call, when the JWT alg starts
  with `HS`, meaning a symmetric secret.
    - The matcher covers every page, RSC prefetch and server-action POST.
    - `ProjectLog` also calls `getUser()`.
    - So a signed-in page load can make 2 or more round trips to Auth. Local
  verification only happens with asymmetric signing keys.
  - **Suggested change:** check whether the hosted project uses asymmetric JWT
  signing keys. If it doesn't, either turn them on or accept the cost knowingly.
  - **Not verified:** the project's signing-key setup.

  **R3. Risk, nit: the matcher only skips image extensions, so other public
  files get redirected. Confidence: medium.**
  - **Where:** `src/proxy.ts:13`
  - **Evidence:**
    ```
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp
  |ico)$).*)"
    ```
  - **Issue:** Any future public file such as `robots.txt`, `sitemap.xml`,
  `manifest.webmanifest` or fonts would 307 to `/sign-in` for signed-out
  visitors, and each pays a `getClaims` call. `public/` holds only `.svg` files
  today, so nothing breaks now.
  - **Suggested change:** add the extensions when such files are added.
  Optionally exclude `api` and return 401 there instead of an HTML redirect once
  route handlers exist.

  cache headers if Supabase called it twice. Confidence: low.**

  - **Evidence:** `response = NextResponse.next({ request });` on each call.
  - **Issue:** The installed `@supabase/ssr` types (`types.d.ts` line 34) say
