## What this is

OnTrack: a shared contribution log for teams (CS6983 AI Coding, Fall 2026, Project 3). Overseers create projects and share an invite code; Contributors join and log entries (date, hours, type, details, optional link; meetings also record attendees, decisions, action items). Overseers see a per-contributor summary, and anyone on a project can download a summary or detailed PDF report.

The product spec is imported above from `docs/PRD.md`. Treat its "Rules the logic must enforce" section as the source of truth for business logic and the primary target for tests. If a request conflicts with the PRD, stop and ask before building.

## Tech stack

- **Framework:** Next.js 16.4 (App Router) with React 19 and TypeScript 5.
- **Styling:** Tailwind CSS v4, wired through the `@tailwindcss/turbopack` loader in `next.config.ts` (there is no PostCSS config).
- **Database:** PostgreSQL on Supabase.
- **Authentication:** Supabase Auth.
- **Testing:** Vitest 5 with jsdom and React Testing Library; Playwright for end-to-end tests (added in Project 3).
- **Hosting:** Vercel, with a preview deploy per pull request.
- **Runtime:** Node 26 (`.nvmrc`). npm is the package manager (`package-lock.json`).

## Architecture decisions

1. **Business rules are pure functions in `src/lib/`.** Visibility, contribution summary, and entry validation take plain data and return plain data. They import nothing from React, Next.js, or Supabase, so they can be unit-tested without a server.
2. **Roles are per project, not per user.** A membership record links a user to a project with the role `contributor` or `overseer`. Never store a role on the user.
3. **Access is enforced twice.** Server code calls the visibility functions in `src/lib/` before reading or writing, and Postgres Row Level Security enforces the same rules in the database. The UI hiding a button is never the only protection.
4. **All input is validated on the server.** Client-side validation is for user experience only. Server actions and route handlers run the validation functions from `src/lib/` again.
5. **Server Components by default.** Add `"use client"` only for components that need state, effects, or browser APIs.
6. **PDF reports are generated in the browser** from data the user is already allowed to see, so no report endpoint can leak another project's entries.
7. **Out-of-scope features stay out.** The PRD lists them (task lists, timers, notifications, GitHub import, file uploads). Do not add them, even partially.

## Next.js version warning

This repo runs Next.js 16.4 with `cacheComponents: true` and `partialPrefetching: true` in `next.config.ts`. Caching, data fetching, and auth patterns differ from older App Router versions. Before writing server code, consult the bundled docs at `node_modules/next/dist/docs/01-app/` (notably `01-getting-started/06-fetching-data.md`, `08-caching.md`, `07-mutating-data.md`, and `02-guides/authentication-with-cache-components.md`). `AGENTS.md` is regenerated by `next dev`; commit it as is and do not edit it by hand.

## Structure and conventions

### Layout

- `src/app/` is the App Router root. `@/*` maps to `src/*` (tsconfig and vitest both resolve it).
- `src/lib/` holds framework-free logic; tests live beside it in `__tests__/`.
- `docs/` holds the PRD and homework evidence.
- Layout note: `<html>` is `h-full` and `<body>` is `min-h-full flex flex-col`, so page roots should use `flex-1` to fill the viewport.

### Code

- TypeScript strict mode. No `any`; use `unknown` and narrow it.
- Named exports for everything in `src/lib/`. Default exports only where Next.js requires them (pages, layouts).
- Functions in `src/lib/` return a result value for expected failures (for example a list of validation errors) and do not throw for them.
- Use the role names from the PRD exactly: `contributor` and `overseer`. Entry types: `work`, `admin`, `meeting`, `check_in`, `standup`, `async_update`, `planning`, `sprint_planning`, `review`, `retrospective`, `other`.
- File names are kebab-case; React components are PascalCase.

### Git

- One branch per GitHub issue, named `<type>/<issue-number>-short-description`, the same format as Project 2. Types: `feature`, `fix`, `docs`, `chore`, `test`. Examples: `feature/7-log-entries`, `docs/3-claude-md`.
- Conventional Commit prefixes: `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`.
- Every change reaches `main` through a pull request reviewed by the other partner.
- Pull request descriptions state the AI disclosure: percent AI-generated, tool used, and what human review was applied.

## Testing strategy

- **Test-driven development is required for everything in `src/lib/`.** Follow red, green, refactor, with one commit per step:
  1. `test:` add a failing test for one acceptance criterion. Run it and confirm it fails for the expected reason.
  2. `feat:` write the minimum code that makes it pass.
  3. `refactor:` clean up with all tests still passing.
- **Unit tests** (Vitest) cover the pure functions in `src/lib/`. Each rule in the PRD's "Rules the logic must enforce" section has at least one test, including the edge cases it names.
- **Integration tests** (Vitest) cover server actions and route handlers, with the database layer mocked at the boundary.
- **Component tests** (React Testing Library) cover forms and conditional rendering by role.
- **End-to-end tests** (Playwright) cover one full path per role.
- **Coverage target:** 70% or higher overall, and close to 100% for `src/lib/`.
- Run `npm test`, `npm run lint`, `npm run format:check`, and `npm run typecheck` before every commit.

## Hooks

`.claude/settings.json` registers three Claude Code hooks. Their scripts live in `.claude/hooks/`.

- **PreToolUse, guard** (`pre-tool-use-guard.mjs`): before Read, Grep, Edit, Write, NotebookEdit or Bash runs, it blocks the actions this file forbids and tells Claude which rule fired. These are reading or printing `.env*` files (except `.env.example`), editing `AGENTS.md`, `package-lock.json` or `node_modules/`, pushing to `main` (including a bare `git push` while on `main`), and any force push. It also catches globs such as `.env*`, absolute paths, and `git -C <dir>`. If the guard itself errors, it blocks the call. It matches strings, so it misses obfuscated commands, variables, and a `cd` earlier in the same command; the `deny` rules in `permissions` remain a second layer. Its tests are in `.claude/hooks/__tests__/` and run with `npm test`.
- **PostToolUse, format on edit** (`format-edited-file.sh`): after every Edit or Write, runs `prettier --write --ignore-unknown` on that one file. It skips files Prettier does not handle, files in `.prettierignore` (`AGENTS.md`, `package-lock.json`, `docs/`), and files outside the project. If Prettier fails, for example on a syntax error, Claude sees the error. It does not run `eslint --fix`, because autofixes can change behavior; `npm run lint` stays a pre-commit check.
- **Stop, run the tests** (`run-tests-on-stop.sh`): when Claude finishes a turn, runs `vitest run` if anything outside `docs/` has changed. If tests fail, it blocks the stop once and feeds the failure back so Claude fixes it. When `stop_hook_active` is true, Claude is already continuing because of this hook, so the script lets it stop instead of looping. It only looks at uncommitted changes, so code committed during a turn is not re-tested; that is why the four checks run before every commit.

Inspect them with `/hooks`. To turn them off for yourself, set `"disableAllHooks": true` in `.claude/settings.local.json`. Evidence of all three hooks firing is in `docs/hooks/`.

## Do

- Read the relevant PRD rule before writing a test or a function for it.
- Write the test first, and show the failing output before implementing.
- Keep each commit to one step (one failing test, one implementation, one refactor).
- Ask before adding a dependency, and explain why it is needed.
- Check the bundled Next.js docs before using caching, data fetching, or auth APIs.
- Say so plainly when something is uncertain or could not be verified.

## Don't

- Don't write implementation code for `src/lib/` before its failing test is committed.
- Don't change or delete a test to make it pass. If a test is wrong, say why and ask.
- Don't read, print, or commit `.env` files or any secret.
- Don't trust role or project IDs sent from the client; look up the membership on the server.
- Don't return any data, including a project's name, to a user without a membership in that project.
- Don't push directly to `main`, force-push, or rewrite published history.
- Don't edit `AGENTS.md`, `package-lock.json`, or anything in `node_modules/` by hand.
- Don't build anything on the PRD's out-of-scope list.

## Working sessions

- Start a new task with `/clear` so earlier, unrelated context does not leak in.
- Run `/compact` at a natural milestone (for example after a feature's tests pass), and tell it what to keep, such as the current issue number and open decisions.
- Resume the most recent session with `claude --continue` when picking the same task back up.
- Use Plan mode before any change that touches more than one file.
