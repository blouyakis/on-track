### Findings

**R1. Risk, non-blocking: sign-up still reveals which emails have accounts when email confirmation is off. Confidence: medium-high.**
- **Where:** `src/app/auth-actions.ts:61-79`
- **Evidence:**
  ```ts
  if (error) { ... return failure("The account could not be created. ...", email); }
  if (!data.session) { return { status: "success", message: "Check your email ..." } }
  redirect(HOME_PATH);
  ```
- **Issue:** With confirmation off, which is the local stack the PR tested, a new address redirects to `/`. An existing address returns "User already registered", shown as the generic error. The two outcomes differ, so anyone can tell whether an address is registered. The PR itself says "The same address again gives the generic message".
  - The PR body's claim that the generic message "cannot reveal which addresses have accounts" holds for sign-in, but not for sign-up.
  - With confirmation on, Supabase returns an obfuscated user with no session and no error. A new and an existing address then both get "Check your email", which is safe.
- **Why it matters:** issue #20 lists auth errors that don't leak information as an acceptance criterion.
- **Suggested change:** ensure email confirmation is enabled on the hosted Supabase project, and say so in the README or PR. Or narrow the PR claim to sign-in and accept the sign-up leak, which most sites have.
- **Not verified:** the hosted project's confirmation setting.

**R2. Risk/performance, non-blocking: the proxy may call Supabase Auth over the network on every request. Confidence: low-medium.**
- **Where:** `src/utils/supabase/proxy.ts:71` (`await supabase.auth.getClaims()`)
- **Issue:** In the installed auth-js (`GoTrueClient.js` around line 5599), `getClaims` falls back to `getUser()`, a network call, when the JWT alg starts with `HS`, meaning a symmetric secret.
  - The matcher covers every page, RSC prefetch and server-action POST.
  - `ProjectLog` also calls `getUser()`.
  - So a signed-in page load can make 2 or more round trips to Auth. Local verification only happens with asymmetric signing keys.
- **Suggested change:** check whether the hosted project uses asymmetric JWT signing keys. If it doesn't, either turn them on or accept the cost knowingly.
- **Not verified:** the project's signing-key setup.

**R3. Risk, nit: the matcher only skips image extensions, so other public files get redirected. Confidence: medium.**
- **Where:** `src/proxy.ts:13`
- **Evidence:**
  ```
  "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)$).*)"
  ```
- **Issue:** Any future public file such as `robots.txt`, `sitemap.xml`, `manifest.webmanifest` or fonts would 307 to `/sign-in` for signed-out visitors, and each pays a `getClaims` call. `public/` holds only `.svg` files today, so nothing breaks now.
- **Suggested change:** add the extensions when such files are added. Optionally exclude `api` and return 401 there instead of an HTML redirect once route handlers exist.

**R4. Risk, nit: the proxy's `setAll` rebuilds the response, which could drop cache headers if Supabase called it twice. Confidence: low.**
- **Where:** `src/utils/supabase/proxy.ts:27-42`
- **Evidence:** `response = NextResponse.next({ request });` on each call.
- **Issue:** The installed `@supabase/ssr` types (`types.d.ts` line 34) say the cache headers come "only with the first cookie write … empty on later calls". A second call in one request would replace the response and lose `Cache-Control: no-store`.
  - With a single `getClaims` per request this is very unlikely in practice.
  - It is the same pattern as Supabase's own Next.js template.
- **Suggested change (optional):** collect the headers across calls, for example an outer `pendingHeaders` with `Object.assign`, and apply them after rebuilding.

**R5. Risk, nit: the server client ignores Supabase's cache headers. Confidence: low.**
- **Where:** `src/utils/supabase/server.ts:15`
- **Evidence:** `setAll(cookiesToSet)` drops the second `headers` argument.
- **Issue:** When `signIn`, `signUp` or `signOut` set cookies in a server action, the no-store headers are not applied. Server-action POST responses are not normally cached by CDNs, so the practical risk is small.
- **Suggested change:** mention it in a comment, or leave it as is.

**L1. Logic, nit: `signOut` ends the session on every device. Confidence: high.**
- **Where:** `src/app/auth-actions.ts:106`
- **Evidence:** `supabase.auth.signOut()` with the default scope, which is `global`.
- **Issue:** The PR already notes this. Signing out on a laptop also signs the user out on their phone, which users of a "Sign out" button may not expect.
- **Suggested change:** use `signOut({ scope: "local" })` unless global sign-out is wanted. This is a product call; it is fine either way if it's intended.

**Praise. Risk/Logic: the security-sensitive paths are handled well. Confidence: high.**
- No open redirect. Every redirect goes to a constant (`HOME_PATH` or `SIGN_IN_PATH`), and the proxy clears `url.search` (`src/utils/supabase/proxy.ts:54`). There is a test with `?next=/evil`.
- A failed session check counts as signed out (`src/utils/supabase/proxy.ts:67-80`).
- Public paths match exactly, so any new page is protected by default (`src/lib/auth-routes.ts:23`). Tests cover `/sign-in-other`, `/SIGN-IN` and `/sign-in/extra`.
- `ProjectLog` uses the verified `getUser()` and redirects before any `.from()` call (`src/app/project-log.tsx:24-30`), and a test asserts no table is read.
- Passwords are never trimmed, never echoed back, and never logged, all with tests.
- Sign-in errors map to a single generic message.
- The demo server action is removed from the module's exports, not just hidden, and a test checks that.
